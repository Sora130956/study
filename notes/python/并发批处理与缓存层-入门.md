# 并发批处理与缓存层 - 入门教程

## 第 1 节：它是什么（一句话 + 一句类比）

**并发批处理**：在异步环境中，用信号量（Semaphore）控制同时运行的任务数量，避免瞬间发出过多请求触发 API 限流。

**缓存层**：把相同输入的 API 响应存起来，下次遇到相同请求直接返回缓存结果，省钱省时间。

**类比**：

- 并发批处理像餐厅厨房里的炉灶数量限制——虽然有 100 个订单，但只有 5 个灶台，同时最多做 5 道菜，做完一道才能接下一个订单。
- 缓存层像餐厅的"今日推荐"预制菜——第一次做要 10 分钟，后面顾客点同样的菜直接端上桌，1 秒搞定。

## 第 2 节：它解决什么问题 / 为什么需要它

### 不用并发控制会怎样？

假设你要处理 1000 条文本，每条调用一次 LLM API：

```python
# 朴素做法：全部并发发出
tasks = [call_llm(text) for text in texts]  # 1000 个任务
results = await asyncio.gather(*tasks)      # 瞬间发出 1000 个请求
```

**痛点**：

1. OpenAI/Anthropic 有速率限制（如每分钟 500 请求），瞬间 1000 个请求直接被拒绝，返回 429 错误。
2. 即使没限流，服务器也可能因并发连接数过多而崩溃。
3. 本地资源耗尽（文件描述符、内存）。

**问题根源**：异步能力被无限制释放，没有流控机制。

### 不用缓存会怎样？

假设 1000 条文本里有 200 条是重复的（如常见问题、模板化输入）：

```python
# 每次都调用 API，重复输入也重新计费
for text in texts:
    result = await call_llm(text)  # 相同文本也会重新花钱请求
```

**痛点**：

1. 相同输入重复计费，成本翻倍。
2. 响应时间拉长（每次都要等 API 返回）。
3. 浪费 API 配额。

**问题根源**：每次请求都当作全新任务，没有记忆机制。

### 经典应用场景

- **并发批处理**：批量翻译、批量摘要、大规模数据标注、爬虫场景。
- **缓存层**：用户重复提问、模板化内容生成、开发测试阶段（避免重复花钱）。

| ------------------- | -------------------------------- | ------------------------------------- | ----- |

## 第 4 节：从最简单的代码示例开始

### 示例 1：最小可运行版本 - 信号量控制并发数

```python
import asyncio

async def call_llm(text: str) -> str:
    """模拟调用 LLM API，耗时 1 秒"""
    await asyncio.sleep(1)  # 模拟网络请求
    return f"processed: {text}"

async def process_with_semaphore(texts: list[str], max_concurrent: int = 5):
    """用信号量控制并发数"""
    sem = asyncio.Semaphore(max_concurrent)  # 创建信号量，最多 5 个并发
    
    async def limited_call(text: str) -> str:
        async with sem:  # 获取令牌，执行完自动释放
            return await call_llm(text)  # 实际调用 API
    
    # 创建所有任务，但信号量会限制同时执行的数量
    tasks = [limited_call(text) for text in texts]
    results = await asyncio.gather(*tasks)  # 等待所有任务完成
    return results

# 运行示例
texts = [f"text_{i}" for i in range(20)]  # 20 个任务
results = asyncio.run(process_with_semaphore(texts, max_concurrent=5))
```

**逐段解读**：

1. **信号量创建** (`sem = asyncio.Semaphore(5)`)：
   - 初始化 5 个"令牌"，任意时刻最多 5 个任务能持有令牌并执行。
   - 其他任务会在 `async with sem` 处等待，直到有任务释放令牌。
2. **`limited_call`** **函数**：
   - `async with sem` 是关键：进入时获取令牌（如果没有令牌则阻塞等待），退出时自动释放。
   - 包裹 `call_llm`，确保调用前拿到令牌。
3. **任务创建** (`tasks = [...]`)：
   - 虽然创建了 20 个任务，但信号量保证同时只有 5 个在执行 `call_llm`。
   - `asyncio.gather` 会等所有任务完成，但执行顺序由信号量控制。

**这一步你得到了什么**：20 个任务不会瞬间发出 20 个请求，而是始终保持 5 个并发，执行时间约 4 秒（20÷5=4 批，每批 1 秒）。

### 示例 2：加一个真实小需求 - 添加 TTL 缓存层

```python
import asyncio
import time
from typing import Optional

class SimpleCache:
    """简单的 TTL 缓存，支持过期时间"""
    def __init__(self, ttl_seconds: int = 3600):
        self.cache = {}  # 存储格式：{key: (value, expire_time)}
        self.ttl = ttl_seconds
    
    def get(self, key: str) -> Optional[str]:
        """获取缓存，过期返回 None"""
        if key in self.cache:
            value, expire_time = self.cache[key]
            if time.time() < expire_time:  # 未过期
                return value
            else:  # 已过期，删除
                del self.cache[key]
        return None
    
    def set(self, key: str, value: str):
        """设置缓存，记录过期时间"""
        expire_time = time.time() + self.ttl
        self.cache[key] = (value, expire_time)

# 全局缓存实例
cache = SimpleCache(ttl_seconds=3600)  # 缓存 1 小时

async def call_llm_with_cache(text: str) -> str:
    """先查缓存，未命中再调用 API"""
    cached = cache.get(text)  # 用输入文本作为 key
    if cached:
        print(f"Cache hit: {text[:20]}...")
        return cached
    
    # 缓存未命中，调用 API
    print(f"Cache miss: {text[:20]}...")
    result = await call_llm(text)
    cache.set(text, result)  # 写入缓存
    return result

async def process_with_cache_and_semaphore(texts: list[str], max_concurrent: int = 5):
    """并发控制 + 缓存层"""
    sem = asyncio.Semaphore(max_concurrent)
    
    async def limited_call(text: str) -> str:
        async with sem:
            return await call_llm_with_cache(text)  # 带缓存的调用
    
    tasks = [limited_call(text) for text in texts]
    return await asyncio.gather(*tasks)

# 运行示例：模拟重复输入
texts = ["hello"] * 5 + ["world"] * 5 + [f"text_{i}" for i in range(10)]
results = asyncio.run(process_with_cache_and_semaphore(texts))
# 输出：前 5 个 "hello" 只有第一个 miss，后 4 个 hit；"world" 同理
```

**逐段解读**：

1. **`SimpleCache`** **类**：
   - `cache` 字典存储 `(value, expire_time)` 元组。
   - `get` 方法检查过期：`time.time() < expire_time` 为真表示未过期。
   - `set` 方法计算过期时间：当前时间 + TTL。
2. **`call_llm_with_cache`** **函数**：
   - 先 `cache.get(text)`，命中直接返回（省去 API 调用）。
   - 未命中才调用 `call_llm`，并将结果写入缓存。
   - **缓存 key**：直接用输入文本（生产环境可能需要 hash）。
3. **组合使用**：
   - 信号量控制并发数，缓存减少实际 API 调用。
   - 对于重复输入（如示例中的 5 个 "hello"），只有第一个会调用 API，其他 4 个直接返回缓存。

**这一步你得到了什么**：20 个任务中，10 个是重复的，实际只调用 API 10 次，节省 50% 成本和时间。

### 示例 3：贴近项目的样子 - 完整的批处理函数

```python
import asyncio
import hashlib
import time
from typing import Optional, Callable

class TTLCache:
    """生产级 TTL 缓存，支持 hash key"""
    def __init__(self, ttl_seconds: int = 3600):
        self.cache = {}
        self.ttl = ttl_seconds
    
    def _make_key(self, text: str) -> str:
        """生成缓存 key：对长文本用 hash 避免内存浪费"""
        if len(text) > 100:
            return hashlib.md5(text.encode()).hexdigest()
        return text
    
    def get(self, text: str) -> Optional[str]:
        key = self._make_key(text)
        if key in self.cache:
            value, expire_time = self.cache[key]
            if time.time() < expire_time:
                return value
            del self.cache[key]
        return None
    
    def set(self, text: str, value: str):
        key = self._make_key(text)
        self.cache[key] = (value, time.time() + self.ttl)

class ConcurrentBatchProcessor:
    """并发批处理器：信号量 + 缓存 + 错误处理"""
    def __init__(
        self,
        llm_func: Callable,  # LLM 调用函数
        max_concurrent: int = 5,
        cache_ttl: int = 3600,
        enable_cache: bool = True
    ):
        self.llm_func = llm_func
        self.sem = asyncio.Semaphore(max_concurrent)
        self.cache = TTLCache(cache_ttl) if enable_cache else None
    
    async def process_one(self, text: str) -> dict:
        """处理单条文本，返回结果或错误"""
        # 1. 尝试缓存
        if self.cache:
            cached = self.cache.get(text)
            if cached:
                return {"text": text, "result": cached, "from_cache": True}
        
        # 2. 信号量控制并发
        async with self.sem:
            try:
                result = await self.llm_func(text)
                if self.cache:
                    self.cache.set(text, result)
                return {"text": text, "result": result, "from_cache": False}
            except Exception as e:
                return {"text": text, "error": str(e), "from_cache": False}
    
    async def process_batch(self, texts: list[str]) -> list[dict]:
        """批量处理，返回所有结果（含错误）"""
        tasks = [self.process_one(text) for text in texts]
        return await asyncio.gather(*tasks, return_exceptions=False)

# 使用示例
async def my_llm_call(text: str) -> str:
    """实际项目中替换为真实 API 调用"""
    await asyncio.sleep(0.5)  # 模拟 API 延迟
    if "error" in text:
        raise ValueError("模拟 API 错误")
    return f"LLM result for: {text}"

async def main():
    processor = ConcurrentBatchProcessor(
        llm_func=my_llm_call,
        max_concurrent=10,  # 允许 10 个并发
        cache_ttl=3600,     # 缓存 1 小时
        enable_cache=True
    )
    
    # 测试数据：包含重复和错误
    texts = ["hello"] * 3 + ["world"] * 2 + ["error_case", "unique_text"]
    results = await processor.process_batch(texts)
    
    # 打印结果
    for r in results:
        if "error" in r:
            print(f"❌ {r['text']}: {r['error']}")
        else:
            cache_flag = "🔵" if r["from_cache"] else "🟢"
            print(f"{cache_flag} {r['text']}: {r['result'][:30]}...")

asyncio.run(main())
```

**逐段解读**：

1. **`TTLCache._make_key`**：
   - 长文本（>100 字符）用 MD5 hash 作为 key，避免字典 key 过大。
   - 短文本直接用原文作为 key。
2. **`ConcurrentBatchProcessor`** **类**：
   - 封装信号量和缓存，提供统一接口。
   - `process_one` 方法处理单条：先查缓存 → 获取信号量 → 调用 API → 写缓存。
   - `process_batch` 方法批量处理：创建所有任务，用 `gather` 并发执行。
3. **错误处理**：
   - `try-except` 捕获 API 异常，返回 `{"error": ...}` 而不是让整个批次失败。
   - 调用方可以区分成功和失败的任务。
4. **返回格式**：
   - 统一返回字典，包含 `from_cache` 标识，方便追踪缓存命中率。

**这一步你得到了什么**：一个可直接用于生产的批处理工具类，支持配置并发数、缓存开关、错误隔离。

```python

from openai import AsyncOpenAI  # 真实 LLM SDK
from concurrent_batch_processor import ConcurrentBatchProcessor  # 上面的类

# 初始化 OpenAI 客户端（必须）
client = AsyncOpenAI(api_key="your-api-key")

async def call_openai_api(text: str) -> str:
    """真实的 LLM 调用（必须）"""
    response = await client.chat.completions.create(
        model="gpt-3.5-turbo",
        messages=[{"role": "user", "content": text}],
        timeout=30.0  # 超时设置（推荐）
    )

        enable_cache=True    # 生产环境按需开关（可选）
    )
    
    # 读取待处理数据（必须）
    texts = load_texts_from_file("input.txt")  # 你的数据源
    
    # 批量处理（必须）
```

**关键配置说明**：

1. **`max_concurrent`** **如何设置**（必须调整）：

   - 计算：`max_concurrent ≈ RPM / 60 × 平均响应时间（秒）`，如 3500/60 × 2 ≈ 116，可设为 50-100。
2. **缓存开关**（按需配置）：
   - 开发/测试阶段：`enable_cache=True`，避免重复花钱。
   - 生产环境：如果输入几乎不重复，可关闭缓存节省内存。
3. **错误处理**（进阶，可先跳过）：
   - 结合重试机制：在 `call_openai_api` 里加 `tenacity` 库自动重试 429 错误。
   - 降级策略：主模型失败时切换到备用模型（见第四周周二内容）。

## 第 6 节：常见坑与易错点

### 坑 1：信号量设置过大仍然触发限流

**现象**：设置 `max_concurrent=100`，仍然收到大量 429 错误。

**原因**：只控制了本地并发数，但没考虑 API 的时间窗口限制（如每分钟 500 请求）。100 个并发如果平均 1 秒完成，30 秒内就会发出 3000 个请求，超过限制。

**解决**：

- 计算公式：`max_concurrent ≤ RPM / 60 × 响应时间`。
- 或者加入 `asyncio.sleep` 在每批次间延迟。

***

### 坑 2：缓存 key 用对象导致永远未命中

**现象**：相同文本每次都 miss 缓存。

**原因**：用可变对象（如字典）或对象实例作为 key，Python 会用对象 ID 而非内容判断相等。

**错误示例**：

```python
cache.set({"text": "hello"}, result)  # 字典不能直接做 key
```

**解决**：用不可变类型（字符串、元组）或 hash 值作为 key。

***

### 坑 3：缓存无限增长导致内存溢出

**现象**：程序运行数小时后内存占用持续增长，最终崩溃。

**原因**：TTL 缓存只在 `get` 时删除过期项，如果某些 key 从不再被访问，过期数据会一直占用内存。

**解决**：

- 定期清理：启动后台任务每 10 分钟扫描删除过期项。
- 或使用 `cachetools.TTLCache`（自动清理）。

***

### 坑 4：`asyncio.gather` 一个任务失败导致全部中断

**现象**：1000 个任务中 1 个报错，整个 `gather` 抛出异常，其他 999 个结果丢失。

**原因**：`gather` 默认不捕获异常，一个任务失败会传播异常。

**解决**：在 `process_one` 内部捕获异常返回错误字典，或使用 `gather(..., return_exceptions=True)`。

***

### "和我直觉相反"的提示

**直觉**：信号量会让程序变慢。\
**实际**：信号量防止过载崩溃，长期看反而更快（避免重试和限流惩罚）。

**直觉**：缓存会占很多内存。\
**实际**：LLM 输出文本通常几百字节，缓存 1 万条也只有几 MB；相比节省的 API 费用（1 万次请求可能几百美元），内存成本可忽略。
