# 健壮性：超时、指数退避重试与 429 限流

> **目标读者**：已经会用 httpx 调外部 API，但一遇到"偶发失败""被限流""偶尔卡死"就只能重启服务的人。
> **前置知识**：[httpx-异步客户端](./httpx-异步客户端.md)（尤其是 3.5 节"超时的四个阶段"）、[asyncio-入门](./asyncio-入门.md) 里的 `await` 与 `asyncio.sleep`。
> **学习时长**：约 2.5 小时。第 3 节若你已读过 httpx 教程可略读；第 4 节示例 3 是本文核心，别跳。

> **教学锚点**：限流器部分取自工作区真实代码 `freelancer-job-analyzer/backend/services/api_client.py` 的 `RateLimiter`（滑动窗口）。超时配置对应 `templates/ai-service-template-project/ai-service-template/app/main.py` 里被注释掉的那段 `httpx.Timeout`。

## 1. 它是什么

一句话：**健壮性 = 承认"外部服务一定会失败"，然后提前规定好"失败时等多久、重试几次、什么情况下干脆放弃"。**

生活化类比：**给人打电话**。

- **超时**：拨出去 30 秒没人接，你会挂掉再想办法，而不是举着电话等一整天。
- **指数退避重试**：占线。你不会每隔 0.1 秒重拨一次（那只会让对方更忙），而是等 1 秒、再等 2 秒、再等 4 秒。
- **随机抖动**：办公室 10 个人同时给同一个号码打，如果都严格等 1 秒后重拨，10 个人又会在同一瞬间撞上。所以每人多等一个零点几秒的随机值，把人群错开。
- **限流器**：对方明说了"我这条线一分钟最多接 20 通"。与其打过去被拒绝，不如自己先排队。
- **429 + `Retry-After`**：对方直接告诉你"3 分钟后再打"。那就按他说的等，别自己瞎猜。

| 类比里的东西 | 代码里的东西 |
| --- | --- |
| 响 30 秒没人接就挂 | `httpx.Timeout(30.0, connect=5.0)` |
| 等 1s → 2s → 4s 再重拨 | `delay = base * (2 ** attempt)` |
| 每人多等一个随机零头 | `delay += random.uniform(0, delay * 0.3)` |
| 自己先排队，别硬打 | `RateLimiter.time_until_available()` |
| 对方说"3 分钟后再打" | 读响应头 `Retry-After` |
| 号码根本不存在，别重拨了 | 4xx 不重试，直接失败 |

## 2. 它解决什么问题

### 先看不做防护会怎样

你的代码是这样的：

```python
async def call_llm(prompt: str) -> str:
    resp = await client.post("/v1/chat/completions", json={...})
    return resp.json()["choices"][0]["message"]["content"]
```

本地测试百分百通过。上线之后：

**痛点 1：<mark style="background: #BBFABBA6;">请求永远不返回，服务被拖死。** httpx 默认超时 5 秒，但如果你写了 `timeout=None`（或者用了某些 SDK 的默认值），上游挂起时这个协程就永久挂着。并发几十个之后，连接池耗尽，**所有**请求开始排队，`/health` 也不响应了——上游一个抖动，你整个服务陪葬。</mark>

**痛点 2：<mark style="background: #BBFABBA6;">偶发的 503 变成用户可见的失败。** 云厂商的 API 有约 0.1% 的瞬时错误率。1000 次调用就有 1 次失败。这类错误**重试一次几乎必成功**，但你没重试，于是用户看到"生成失败"。</mark>

**痛点 3：<mark style="background: #BBFABBA6;">一被限流就雪崩。** 收到 429 你不处理，用户重试 → 又 429 → 前端自动重连 → 更多 429。你的请求量在被限流时**反而上涨**，限流窗口永远恢复不了。这叫重试风暴。</mark>

### 问题根源

一句话：**跨网络调用的失败不是"异常情况"，而是常态；默认写法却假设它总会成功。**

更准确地说：<mark style="background: #BBFABBA6;">失败分两类，**瞬时的**（网络抖动、502/503、429）值得重试，**确定的**（401 密钥错、400 参数错）重试一万次也是错。不区分这两类，就只有两种烂选择：都不重试（浪费本可挽救的请求）或都重试（把确定的失败放大成风暴）。</mark>

### 经典应用场景

- 调 OpenAI / Claude 等 LLM API（限流严格、偶发 5xx 多）
- 抓取第三方数据接口（如 job-analyzer 抓职位列表，明确写了每分钟配额）
- 任何"依赖别人服务器"的地方

## 3. 前置知识

### 3.1 超时的四个阶段

**定义**：<mark style="background: #BBFABBA6;">httpx 把一次请求的等待拆成 connect / read / write / pool 四段，各自独立计时。</mark>

**大白话**：`connect` 是"拨号接通要多久"，`read` 是"对方开口说第一个字要多久"，`pool` 是"连接池全占用时你排队等多久"。

```python
# 连接要快（拨不通就早点失败），读可以慢（LLM 生成本来就慢）
timeout = httpx.Timeout(60.0, connect=5.0)
```

详见 [httpx-异步客户端](./httpx-异步客户端.md) 的 3.5 节。本文只强调一点：**这两个值的取舍方向是相反的**——connect 要短（快速失败），read 要长（给模型时间）。

### 3.2 <mark style="background: #BBFABBA6;">哪些错误值得重试</mark>

**定义**：可重试 = 瞬时故障，再试一次条件可能就变了。

**大白话**：服务器说"我现在忙"值得再试；说"你的钥匙不对"再试一万次还是不对。

| 情况 | 重试？ | 理由 |
| --- | --- | --- |
| `ConnectError` / `ReadTimeout` | 是 | 网络抖动 |
| 502 / 503 / 504 | 是 | 上游临时不可用 |
| 429 | 是，但按 `Retry-After` 等 | 被限流，等就好了 |
| 400 / 401 / 403 / 404 | **否** | 你的请求本身有问题，重试只是浪费 |
| 500 | 看情况 | 多数是上游 bug，重试一次即可，别多 |

### 3.3 指数退避（exponential backoff）

**定义**：<mark style="background: #BBFABBA6;">每次重试的等待时间按倍数增长，通常是 2 的幂。</mark>

**大白话**：别人越忙你越要少打扰，所以每失败一次就多等一倍。

```python
delay = 1.0 * (2 ** attempt)   # attempt=0,1,2 → 1s, 2s, 4s
```

### 3.4 抖动（jitter）

**定义**：<mark style="background: #BBFABBA6;">在退避时间上叠加一个随机量。</mark>

**大白话**：<mark style="background: #BBFABBA6;">防止所有客户端在同一毫秒一起回来，把上游第二次打垮。</mark>

```python
delay += random.uniform(0, delay * 0.3)   # 在 delay 基础上随机多等 0~30%
```

### 3.5 滑动窗口限流

**定义**：记下最近 N 次调用的时间戳，丢弃超出窗口的，剩下的数量就是当前窗口内的用量。

**大白话**：像酒吧门口的计数器——记住每个人进门的时刻，一分钟前进的就不算了。

### 3.6 术语速查表

| 术语 | 一句话 |
| --- | --- |
| 超时（timeout） | 等待上限，到点就放弃 |
| 退避（backoff） | 重试前的等待 |
| 指数退避 | 等待时间按倍数增长 |
| 抖动（jitter） | 给等待时间加随机量，避免同步撞车 |
| 429 | HTTP 状态码"请求过多"，即被限流 |
| `Retry-After` | 响应头，上游告诉你隔多久再来（秒数或日期） |
| 限流器（rate limiter） | 客户端**主动**控制发送速率的组件 |
| 重试风暴 | 失败触发重试、重试加剧失败的正反馈 |
| 幂等 | 同一请求做多次和做一次效果相同；不幂等的操作重试有风险 |
| `time.monotonic()` | 单调时钟，不受系统时间调整影响，测间隔必须用它 |

## 4. 三个递进示例

### 示例 1：最小可运行 —— 超时 + 固定次数重试

```python
import asyncio
import httpx


async def fetch_once(client: httpx.AsyncClient, url: str) -> dict:
    resp = await client.get(url)
    # 4xx/5xx 抛 HTTPStatusError。不写这行，错误响应会被当成正常 JSON 解析
    resp.raise_for_status()
    return resp.json()


async def fetch_with_retry(url: str, retries: int = 3) -> dict:
    # connect 给 5 秒：拨不通就赶紧失败，别占着协程
    # 总超时 30 秒：普通 API 够用，LLM 要调大
    timeout = httpx.Timeout(30.0, connect=5.0)

    async with httpx.AsyncClient(timeout=timeout) as client:
        for attempt in range(retries):
            try:
                return await fetch_once(client, url)
            except (httpx.ConnectError, httpx.ReadTimeout) as exc:
                # 最后一次还失败就别吞了，抛出去让调用方知道
                if attempt == retries - 1:
                    raise
                # 1s → 2s → 4s，给上游喘息时间
                delay = 2 ** attempt
                print(f"第 {attempt + 1} 次失败（{type(exc).__name__}），{delay}s 后重试")
                await asyncio.sleep(delay)

    raise RuntimeError("unreachable")   # 循环必然 return 或 raise，这行只为让类型检查满意
```

**逐段解读**

- `httpx.Timeout(30.0, connect=5.0)`：第一个位置参数是**其余三项的默认值**（read/write/pool 都是 30），`connect` 单独覆盖成 5。这个写法就是骨架 `main.py` 里注释掉的那行。
- `resp.raise_for_status()`：httpx 和 requests 一样，**默认不会**因为 500 抛异常。不写这行，你会拿到一个 `{"error": ...}` 的字典然后在 `["choices"]` 那里报 KeyError——错误信息完全指向错误的方向。
- `except (httpx.ConnectError, httpx.ReadTimeout)`：**只捕获这两类**。注意这里**没有**捕获 `HTTPStatusError`，意味着 401 会直接抛出去不重试——这正是我们想要的。
- `if attempt == retries - 1: raise`：最后一次不再退避，直接抛。漏掉这个判断会导致最后多睡一次然后静默返回 `None`。
- `delay = 2 ** attempt`：0→1s，1→2s，2→4s。

**这一步你得到了什么**：能扛住网络抖动的调用。但它有两个明显缺口：**502/503 不会被重试**（因为归在 `HTTPStatusError` 里没捕获），**429 没有特殊处理**。下一步补上。

### 示例 2：加真实需求 —— 区分错误类型 + 尊重 `Retry-After` + 抖动

```python
import asyncio
import logging
import random

import httpx

log = logging.getLogger(__name__)

# 值得重试的状态码：都属于"上游临时不行"或"你太快了"
RETRYABLE_STATUS = {429, 500, 502, 503, 504}


def _parse_retry_after(resp: httpx.Response) -> float | None:
    """从响应头读出上游要求的等待秒数；没有或格式怪就返回 None。"""
    raw = resp.headers.get("Retry-After")
    if not raw:
        return None
    try:
        # 标准允许两种格式：秒数，或 HTTP 日期。这里只处理常见的秒数格式，
        # 日期格式解析失败就退回自己的退避策略，不至于崩
        return float(raw)
    except ValueError:
        return None


def _backoff(attempt: int, base: float = 1.0) -> float:
    """指数退避 + 抖动。attempt 从 0 开始。"""
    delay = base * (2 ** attempt)
    # 加 0~30% 的随机量，避免多个客户端同时醒来再次撞车
    return delay + random.uniform(0, delay * 0.3)


async def request_with_retry(
    client: httpx.AsyncClient,
    method: str,
    url: str,
    *,
    retries: int = 3,
    **kwargs,
) -> httpx.Response:
    last_exc: Exception | None = None

    for attempt in range(retries):
        try:
            resp = await client.request(method, url, **kwargs)

            # 状态码正常，直接返回，不进重试逻辑
            if resp.status_code not in RETRYABLE_STATUS:
                resp.raise_for_status()   # 4xx 在这里抛出去，不重试
                return resp

            # 到这说明是可重试状态码。最后一次就别等了，直接抛
            if attempt == retries - 1:
                resp.raise_for_status()

            # 上游明说了等多久就听它的；没说才用自己的退避
            wait = _parse_retry_after(resp) or _backoff(attempt)
            log.warning(
                "upstream %s, retrying in %.1fs (attempt %d/%d)",
                resp.status_code, wait, attempt + 1, retries,
            )

        except (httpx.ConnectError, httpx.ReadTimeout, httpx.WriteTimeout) as exc:
            # 网络层错误：没有响应可读，只能用自己的退避
            last_exc = exc
            if attempt == retries - 1:
                raise
            wait = _backoff(attempt)
            log.warning("network error %s, retrying in %.1fs", type(exc).__name__, wait)

        await asyncio.sleep(wait)

    raise last_exc or RuntimeError("retry loop exhausted")
```

**逐段解读**

- `RETRYABLE_STATUS`：把"哪些值得重试"从代码逻辑里抽成一个常量。以后想调整（比如决定 500 不再重试）只改一处。
- `if resp.status_code not in RETRYABLE_STATUS: resp.raise_for_status(); return resp`：这两行是**错误分类的分水岭**。401/400 走 `raise_for_status()` 立即抛出，永远不会进入重试；200 直接返回。
- `_parse_retry_after(resp) or _backoff(attempt)`：**优先听上游的**。上游知道自己的限流窗口什么时候重置，你的 `2 ** attempt` 只是瞎猜。这是处理 429 的正确姿势。
- `except ValueError: return None`：`Retry-After` 也允许是 HTTP 日期格式。这里不处理日期，但**解析失败必须退回到自己的退避**，而不是让整个调用崩掉——健壮性代码自己先崩了是最尴尬的。
- `random.uniform(0, delay * 0.3)`：抖动。如果你的服务有 20 个 worker 同时被限流，没有抖动它们会在同一秒一起重试，第二次一起 429。
- **`if attempt == retries - 1: resp.raise_for_status()`** 出现在 sleep 之前：最后一次不睡，直接抛出带状态码的异常。

**这一步你得到了什么**：一个会区分错误类型、会听上游指令、不会制造重试风暴的调用函数。但它仍然是**被动的**——只有被拒绝了才知道要慢下来。下一步做主动限流。

### 示例 3：贴近项目 —— 主动限流（取自 job-analyzer 真实代码）

被动重试是"撞墙再退"，主动限流是"知道墙在哪，提前刹车"。真实代码见 `freelancer-job-analyzer/backend/services/api_client.py`。

```python
import asyncio
import time
from typing import List


class RateLimiter:
    """滑动窗口限流器：保证 period 秒内调用次数不超过 max_calls。"""

    def __init__(self, max_calls: int, period: float):
        self.max_calls = max_calls
        self.period = period
        # 记录每次调用发生的时刻。用 monotonic 时间而不是 time.time()，
        # 因为后者会被系统对时/夏令时改动，导致窗口计算错乱
        self._calls: List[float] = []

    def _prune(self, now: float) -> None:
        """丢掉窗口之外的旧时间戳 —— 它们已经不占额度了。"""
        cutoff = now - self.period
        self._calls = [t for t in self._calls if t > cutoff]

    def time_until_available(self) -> float:
        """还要等几秒才能发下一个请求（0 表示可以立刻发）。"""
        now = time.monotonic()
        self._prune(now)

        # 窗口里还有空位，不用等
        if len(self._calls) < self.max_calls:
            return 0.0

        # 满了。最早那次调用滑出窗口的时刻，就是下一个空位出现的时刻
        oldest = self._calls[0]
        return max(0.0, oldest + self.period - now)

    def record(self) -> None:
        """登记一次调用。必须在真正发出请求时调用。"""
        self._calls.append(time.monotonic())


class ApiClient:
    def __init__(self, settings):
        # 两个窗口同时生效：既不能超每分钟配额，也不能超每小时配额。
        # 很多 API 就是这样双层限流的
        self.minute_limiter = RateLimiter(max_calls=settings.RATE_LIMIT_PER_MINUTE, period=60)
        self.hour_limiter = RateLimiter(max_calls=settings.RATE_LIMIT_PER_HOUR, period=3600)
        self._client = httpx.AsyncClient(
            base_url=settings.BASE_URL,
            timeout=httpx.Timeout(30.0, connect=5.0),
        )

    async def _throttle(self) -> None:
        """等到两个窗口都允许发送为止。"""
        for limiter in (self.minute_limiter, self.hour_limiter):
            wait = limiter.time_until_available()
            if wait > 0:
                # 主动睡，而不是发出去挨 429。省掉一次往返，也不给上游添乱
                await asyncio.sleep(wait)

    async def get(self, path: str, params: dict | None = None) -> dict:
        await self._throttle()
        # 关键顺序：先 record 再发请求。
        # 如果反过来（发完再记），并发场景下多个协程会同时通过 _throttle 检查，
        # 一起冲出去，瞬间超额
        self.minute_limiter.record()
        self.hour_limiter.record()

        resp = await request_with_retry(self._client, "GET", path, params=params)
        return resp.json()
```

**逐段解读**

- `time.monotonic()` 而非 `time.time()`：单调时钟只会往前走，不受 NTP 对时影响。**所有"测量时间间隔"的场景都该用它**（[ttl-缓存](./ttl-缓存.md) 里 `expires_at` 也是这个理由）。
- `_prune`：每次查询时顺手清理过期时间戳，所以列表长度天然被 `max_calls` 约束住，不会无限增长。
- `oldest + self.period - now`：窗口满了时，最早那次调用在 `oldest + period` 时刻滑出，那一刻就空出一个名额。这个式子就是"还要等多久"。
- **两个限流器串行检查**：先等分钟窗口，再等小时窗口。因为等完分钟窗口后时间已经推进了，小时窗口要重新算。
- **`record()` 必须在请求前调用**：这是最容易写反的一行。如果先发请求、返回后再 `record()`，那么 10 个并发协程会在同一时刻都看到"窗口里 0 次调用"，然后一起发出去。**先登记再发送**才能让后来者看到已占用的额度。
- `await asyncio.sleep(wait)` 而不是阻塞 sleep：睡的期间事件循环去处理别的请求，服务不会僵住。

**主动限流 vs 被动重试，要哪个？**

**都要**。它们防的不是同一件事：

| | 主动限流 | 被动重试 |
| --- | --- | --- |
| 时机 | 请求发出**前** | 请求失败**后** |
| 防什么 | 自己把配额打爆 | 上游抖动、别的实例把配额打爆 |
| 前提 | 你知道配额数字 | 不需要知道 |
| 缺口 | 多实例部署时各算各的，仍会超 | 不知道配额，只能撞了才退 |

多实例部署时主动限流会失效（每个进程各有一套计数器），这时被动重试是最后一道防线。

**这一步你得到了什么**：一条完整的防线——主动刹车避免大部分 429，撞上了也能按 `Retry-After` 优雅退避，网络抖动能自愈，而 401 这类确定错误会立刻失败不浪费时间。

## 5. 最小可用的实际用法

贴进骨架 `app/` 下新建的 `retry.py`，然后在 `main.py` 的 `lifespan` 里配好 client：

```python
# app/retry.py
import asyncio
import logging
import random

import httpx

log = logging.getLogger(__name__)

RETRYABLE = {429, 500, 502, 503, 504}          # 必须


def _backoff(attempt: int, base: float = 1.0) -> float:   # 必须
    delay = base * (2 ** attempt)
    return delay + random.uniform(0, delay * 0.3)          # 必须：抖动


async def request_with_retry(client, method, url, *, retries=3, **kwargs):
    for attempt in range(retries):
        try:
            resp = await client.request(method, url, **kwargs)
            if resp.status_code not in RETRYABLE:
                resp.raise_for_status()                    # 必须：4xx 不重试
                return resp
            if attempt == retries - 1:
                resp.raise_for_status()
            raw = resp.headers.get("Retry-After")           # 必须：429 要听上游的
            wait = float(raw) if raw and raw.isdigit() else _backoff(attempt)
        except (httpx.ConnectError, httpx.ReadTimeout, httpx.WriteTimeout):
            if attempt == retries - 1:
                raise
            wait = _backoff(attempt)
        log.warning("retrying %s %s in %.1fs", method, url, wait)
        await asyncio.sleep(wait)
```

```python
# app/main.py 的 lifespan 里
client = httpx.AsyncClient(
    base_url=settings.base_url,
    timeout=httpx.Timeout(60.0, connect=5.0),   # 必须：LLM 读超时给足，连接超时要短
    limits=httpx.Limits(max_connections=50),    # 可选：限制并发连接数
)
app.state.http_client = client
```

**可选 / 可跳过的进阶项**：

- **主动限流器（示例 3 的 `RateLimiter`）**：只有当上游有明确配额、且你**单实例**部署时才划算。刚起步先用被动重试，等真的频繁吃 429 再加。**可跳过**。
- **`tenacity` 库**：用装饰器写重试（`@retry(wait=wait_exponential(), stop=stop_after_attempt(3))`），比手写简洁。但它对"读 `Retry-After`"的支持要写自定义 wait 函数，反而更绕。手写 30 行更透明。**可跳过**。
- **熔断器（circuit breaker）**：上游连续失败 N 次后，一段时间内直接拒绝新请求不再尝试。单个小服务用不上。**跳过**。
- **幂等性考量**：POST 创建资源类的请求重试可能导致重复创建。LLM 的 chat completions 是无副作用的，重试安全。做支付、下单时才需要 idempotency key。**当前项目可跳过**。

**怎么测**：见 [respx-http-mock](./respx-http-mock.md)。要点：
- 用 `side_effect=[Response(429, headers={"Retry-After": "2"}), Response(200, json={...})]` 模拟"先限流再成功"
- 用 `monkeypatch` 把 `asyncio.sleep` 打桩成立即返回，否则测试要真睡 2 秒
- 断言**最终业务结果正确** + `route.call_count == 2`，而不是只断言没抛异常
- 自证有效性：把 `RETRYABLE` 里的 429 删掉，测试必须变红

## 6. 常见坑与易错点

### 坑 1：把 4xx 也重试了

**现象**：API key 写错，服务卡住 7 秒才报错；日志里同一个 401 出现 3 次。

**原因**：`except httpx.HTTPStatusError` 捕获得太宽，或者直接 `except Exception` 一把梭。401 重试一万次还是 401。

**解决**：明确列出可重试的状态码集合，其余的立刻 `raise_for_status()` 抛出。

---

### 坑 2：收到 429 用自己的退避，忽略 `Retry-After`

**现象**：限流后重试全部失败，日志里 429 密集出现，配额迟迟不恢复。

**原因**：上游说"60 秒后再来"，你按 `2 ** attempt` 只等了 1s、2s、4s，三次全撞在限流窗口里，而且每次撞击都可能**延长**窗口。

**解决**：`_parse_retry_after(resp) or _backoff(attempt)` —— 上游有指令就听指令。

---

### 坑 3：没有抖动，多实例同时重试

**现象**：单实例跑得好好的，扩到 5 个实例后 429 暴增。

**原因**：5 个实例在同一时刻被限流，各自等 1 秒，然后**在同一毫秒**一起回来。上游看到的瞬时并发和第一次一样高。

**解决**：`delay + random.uniform(0, delay * 0.3)`。一行代码，效果显著。

---

### 坑 4：`record()` 写在请求之后

**现象**：限流器配了每分钟 20 次，实际日志里一分钟发出去 60 次。

**原因**：并发场景下，10 个协程同时通过 `_throttle()` 检查（此时窗口里确实还空着），然后一起发请求，请求返回后才各自 `record()`。检查和登记之间存在竞态窗口。

**解决**：`_throttle()` 之后**立刻** `record()`，再发请求。对极高并发还需要加 `asyncio.Lock` 把"检查+登记"变成原子操作。

---

### 坑 5：超时设成一个值，connect 和 read 一刀切

**现象**：要么 LLM 长回答总是被切断（超时设太短），要么上游挂掉时协程堆积（超时设太长）。

**原因**：`timeout=60` 会让 connect 也等 60 秒。而连接建立本该在 1 秒内完成——等 60 秒只是白白占着一个协程和一个连接池槽位。

**解决**：`httpx.Timeout(60.0, connect=5.0)`。方向记住：**connect 短、read 长**。

---

### 和直觉相反的一点

**重试会让系统在故障时更脆弱，而不是更健壮。**

直觉是"多试几次总能成功"。但算一下：上游负载过高开始返回 503。你配了 3 次重试，于是每个失败请求变成 3 个请求——**上游收到的流量瞬间变成 3 倍**。原本只是过载的服务，被重试彻底压垮。恢复过来后，积压的请求又一起涌入，再次压垮。

这就是为什么"退避"和"抖动"不是可选装饰，而是重试的**必要组成部分**：

- 没有退避的重试 = 立即放大流量
- 没有抖动的退避 = 把流量集中到几个尖峰
- 没有错误分类的重试 = 把确定的失败也放大

**记住这条判断标准：如果你的重试逻辑会让上游在故障时收到更多请求，那它就是在制造故障，而不是在容错。**
