# LLM API 错误处理：错误分类、重试与降级

- **目标读者**：已会调 OpenAI/DeepSeek SDK、写过流式输出，但还没处理过线上失败的人
- **前置知识**：[openai-api-入门.md](./openai-api-入门.md)（messages 结构）、[流式输出-streaming-入门.md](./流式输出-streaming-入门.md)（`stream=True` 与 SSE）
- **学习时长**：约 30 分钟
- **可跳过的节**：已读过 [健壮性-超时重试限流.md](./健壮性-超时重试限流.md) 的话，第 1~2 节扫一眼即可，核心是第 4 节示例 3（流式的重试边界）

---

## 第 1 节：它是什么

**一句话定义**：错误处理是给 LLM 调用套上的三层保护——先把失败**分类**（值不值得重试），可重试的就**退避重试**，重试全失败就**降级**到备用模型。

**生活化类比**：点外卖。

- 餐厅爆单出餐慢（429/5xx/超时）→ 等一会儿再催一次，催 3 次还不行就放弃 → **重试**
- 这家店今天关门了（催一万次也没用）→ 换一家店 → **降级**
- 你把收货地址写错了（400 参数错）→ 催一万次也送不到，直接报错 → **不重试**

---

## 第 2 节：它解决什么问题

### 不做会怎样？

**痛点 1：偶发失败直接砸到用户脸上。** LLM API 有千分之一级别的瞬时 5xx，重试一次几乎必成功。不重试，用户就看到「生成失败」。

**痛点 2：乱重试引发风暴。** 400 参数错、401 key 失效也重试，请求量翻倍，429 限流永远恢复不了。

**痛点 3：流式响应乱重试会输出重复内容。** 用户已经看到前半段回答，你后台悄悄重试，LLM 从头又生成一遍，前端把两遍拼在一起——回答变成「你好你好……」。**流式的重试有边界，这是本文的核心。**

**问题根源**：失败分「瞬时」（值得重试）和「确定」（重试无用）两类；流式响应一旦开始吐字就不能从头再来。

## 第 3 节：读下去之前，先搞懂这些概念

| 术语 | 大白话解释 | 最小示例 | 对应正文 |
|------|-----------|---------|---------|
| **tenacity** | Python 重试库，一个装饰器搞定「试几次、等多久、什么错误才重试」 | `@retry(stop=stop_after_attempt(3))` | 第 4 节示例 1 |
| **APIStatusError** | OpenAI SDK 抛出的 HTTP 错误，带 `status_code` 属性 | `e.status_code == 429` | 第 4 节示例 2 |
| **Retry-After** | 429 响应头，服务器明说「几秒后再来」 | `e.response.headers["retry-after"]` | 第 6 节坑 3 |
| **SSE error event** | 流式中途失败时，发给前端的自定义错误事件 | `event: error\ndata: ...` | 第 4 节示例 3 |
| **降级（fallback）** | 主模型重试全失败后，换备用模型再试 | DeepSeek → 通义千问 | 第 4 节示例 3 |

## 第 4 节：从最简单的代码示例开始

### 示例 1：最小可运行版本 —— 非流式调用加重试

**目标**：用 tenacity 一个装饰器，让失败自动重试 3 次。

```python
from openai import OpenAI
from tenacity import retry, stop_after_attempt, wait_exponential

client = OpenAI(api_key="your-key", base_url="https://api.deepseek.com")

@retry(
    stop=stop_after_attempt(3),                    # 最多试 3 次（含首次）
    wait=wait_exponential(multiplier=1, min=1, max=10),  # 等 1s → 2s → 4s…封顶 10s
    reraise=True,                                  # 3 次都失败，把最后一次异常抛出来
)
def create_completion(messages: list[dict]) -> str:
    """调 LLM 并返回文本，失败自动重试"""
    resp = client.chat.completions.create(model="deepseek-chat", messages=messages)
    return resp.choices[0].message.content
```

**逐段解读**：

1. **`@retry` 装饰器**：包在函数外面，函数抛异常时按规则自动再调一次。等价于手写 `for attempt in range(3): try: ... except: sleep(...)`，但不用自己写循环。
2. **`wait_exponential`**：指数退避——每次等待时间翻倍，避免固定间隔重试把服务器打得更惨（原理详见 [健壮性-超时重试限流.md](./健壮性-超时重试限流.md)）。
3. **`reraise=True`**：不加的话重试耗尽会抛 tenacity 自己的 `RetryError`，加了就抛原始异常，上层好处理。

**这一步你得到了什么**：任何函数加上 `@retry` 就有了自动重试能力。

### 示例 2：加真实需求 —— 只重试「值得重试」的错误

**目标**：429/5xx/超时重试，400/401 直接失败。

```python
import openai
from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception

def is_retryable(e: Exception) -> bool:
    """判断这个错误值不值得重试：值得返回 True，tenacity 才会重试"""
    # HTTP 状态码错误：429（限流）和 5xx（服务器抽风）可重试
    if isinstance(e, openai.APIStatusError):
        return e.status_code in (429, 500, 502, 503, 504)
    # 网络层错误：超时、连接失败可重试
    return isinstance(e, (openai.APITimeoutError, openai.APIConnectionError))

# 把示例 1 的固定重试换成「按错误类型决定」
@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=1, max=10),
    retry=retry_if_exception(is_retryable),  # 关键：只有 is_retryable 返回 True 才重试
    reraise=True,
)
def create_completion(messages: list[dict]) -> str:
    resp = client.chat.completions.create(model="deepseek-chat", messages=messages)
    return resp.choices[0].message.content
```

**逐段解读**：

1. **`retry_if_exception(is_retryable)`**：tenacity 每次捕获异常后先调这个函数，返回 `False` 就直接抛出不重试。400（参数错）、401（key 错）走到这里返回 `False`，一次都不会重试。
2. **`openai.APIStatusError`**：SDK 把所有 HTTP 错误统一成这个异常，用 `e.status_code` 区分。
3. **超时和连接错误没有状态码**：`APITimeoutError` / `APIConnectionError` 是网络层异常，单独判断。

**这一步你得到了什么**：一个带「错误分类」的重试函数，这是「重试与降级」里的前半句。

### 示例 3：贴近项目 —— 流式输出 + SSE + 降级

**目标**：接 W2 的 SSE 接口。关键约束：**重试只能发生在第一个 chunk 到达之前**。

```python
from collections.abc import Generator

import openai
from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=1, max=10),
    retry=retry_if_exception(is_retryable),  # is_retryable 见示例 2
    reraise=True,
)
def create_stream(messages: list[dict], model: str):
    """只负责「创建流」。装饰器的重试只覆盖这一步，不覆盖后面的迭代"""
    return client.chat.completions.create(model=model, messages=messages, stream=True)


def sse_generator(messages: list[dict]) -> Generator[str, None, None]:
    """FastAPI StreamingResponse 用的生成器，产出 SSE 格式的字符串"""
    # ---------- 第一层：重试（只包创建流）----------
    try:
        stream = create_stream(messages, model="deepseek-chat")
    except openai.APIError:
        # ---------- 第二层：降级（主模型重试 3 次全失败，换备用模型）----------
        try:
            stream = create_stream(messages, model="qwen-plus")
        except openai.APIError as e:
            yield f"event: error\ndata: 服务暂时不可用：{e}\n\n"
            return

    # ---------- 迭代阶段：不再重试，失败只能通知前端 ----------
    try:
        for chunk in stream:
            content = chunk.choices[0].delta.content or ""
            yield f"data: {content}\n\n"
    except openai.APIError as e:
        # 流到一半断了。此时前端已收到部分内容，重试会重复输出，只能报错收尾
        yield f"event: error\ndata: 生成中断：{e}\n\n"
```

**逐段解读**：

1. **为什么装饰器只包 `create_stream`**：`create()` 返回只代表连接建立、流对象拿到手。重试窗口 = 从发请求到第一个 chunk 到达之前。这期间重试是安全的，因为前端一个字都还没收到。
2. **迭代阶段为什么不重试**：`for chunk in stream` 循环里每次 `yield` 都把内容发给了前端。如果第 50 个 chunk 断线时重试，LLM 会从头重新生成，前端把新旧两遍拼起来，输出就乱了。所以中途失败只能发 `event: error` 通知前端，由前端决定要不要整个重新发起。
3. **降级是独立的一层**：重试是「同一个模型再试几次」，降级是「这个模型不行了换一个」。顺序是先重试、耗尽后降级，不是每次重试都换模型。
4. **SSE error event**：前端 `EventSource` 里用 `addEventListener('error', ...)` 监听，和普通 `data:` 消息区分开。

**这一步你得到了什么**：一套可直接用在 FastAPI SSE 接口里的「重试 + 降级」骨架，也是 W4 周二「多模型降级」的雏形。

## 第 5 节：最小可用的实际用法

真实项目里把三层组装起来的完整模板：

```python
from openai import OpenAI

# 必须：max_retries=0 关掉 SDK 自带重试，避免和 tenacity 相乘（见第 6 节坑 1）
client = OpenAI(api_key="...", base_url="...", max_retries=0)

# 必须：错误分类 + 重试装饰器（第 4 节示例 2 原样搬过来）
# 必须：非流式 → 装饰器包整个调用
# 必须：流式   → 装饰器只包 create_stream，迭代单独 try/except 发 SSE error
# 可选：降级链（主模型 → 备用模型），小项目只有一个 key 时可省
# 可选：429 时读 Retry-After 响应头决定等待时间（进阶，见第 6 节坑 3）
```

**通常会搭配**（进阶，可先跳过）：结构化日志记录每次重试（`structlog`）、按模型统计失败率、备用模型用不同厂商的 key。

## 第 6 节：常见坑与易错点

### 坑 1：SDK 自带重试和 tenacity 相乘

**现象**：429 之后等了远超预期的时间才报错。

**原因**：OpenAI SDK 默认 `max_retries=2`，你在 tenacity 里又设 3 次，实际最多请求 3×3=9 次，等待时间相乘。

**解决**：`OpenAI(max_retries=0)` 关掉 SDK 层重试，重试逻辑只留在 tenacity 一处，行为可预测。

### 坑 2：以为流式中途断了也能重试

**现象**：断线后自动重试，前端输出内容重复出现两遍。

**原因**：流式响应一旦开始吐 chunk，前端已经消费了部分内容，重试只能从头生成，无法「续上」。

**解决**：牢记重试边界——装饰器只包「创建流」，迭代阶段的异常发 `event: error` 通知前端重新发起。

### 坑 3：429 时无视 Retry-After 自己瞎等

**现象**：指数退避等 1s、2s、4s，但服务器明确说了 60 秒内别来，重试全部白费。

**原因**：429 响应头里的 `Retry-After` 是服务器的明确指令，优先级高于你的退避计算。

**解决**：进阶做法是自定义 tenacity 的 `wait` 函数，优先读 `e.response.headers.get("retry-after")`。入门阶段示例 2 的固定退避够用。

### 坑 4：降级到备用模型，输出格式变了

**现象**：主模型挂了切备用模型，结果下游 JSON 解析报错。

**原因**：不同模型对同一 prompt 的输出习惯不同（比如一个给纯 JSON，一个爱加 ```json 代码块）。

**解决**：降级模型的选择要验证过输出兼容性，结构化输出场景优先用同样支持 `response_format` 的模型。

### 和直觉相反的点：重试不是越多越久越好

直觉上「多试几次、多等一会儿成功率高」，但 429 限流场景下，所有客户端都猛重试会让限流窗口永远恢复不了（重试风暴）。**3 次 + 指数退避是业界甜点位**，超过这个量级就该降级或报错，把压力释放掉。
